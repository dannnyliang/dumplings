## Context

Dumplings 目前的記帳模型是「單一共同帳戶 + 例外標記」：一切預設從共同帳戶出，非共同帳戶支付的就標記為代墊、還清時打勾。實際使用後發現這個模型描述不了真實的付款情境，且首頁的數字不可信（詳見 proposal.md）。

本次重新設計的需求來自使用者本人，關鍵前提如下（皆為使用者明確確認的答案，不是推測）：

- **只有兩位使用者**（Danny、PeiYu），手機操作為主
- **「應計 vs 現金」要解決的是兩件事**：刷卡日與帳單扣款日的落差、墊付與實際結算的落差。**不需要**年繳費用攤提，**不需要**應付帳款
- **資金流動是混合模式**：大額走共同帳戶、日常各自付，沒有固定規則
- **只記共同開銷**：個人花費（自己的衣服、興趣、與朋友吃飯）不進這個 app
- **個人帳戶與個人信用卡視為相同**：對本 app 而言都是「某人先出錢，共同帳戶欠他」
- **現有的 `'credit_card'` 值指的是一張為共同帳戶辦的卡**，帳單從共同帳戶扣款
- 圖表非必要，重點是能分析每月各分類的支出狀況

## Goals / Non-Goals

**Goals:**

- 使用者不需理解「應計基礎」「現金基礎」等會計名詞，就能同時看到「已經花掉多少」與「帳戶實際還有多少」
- 結算成為有日期、有金額的獨立事件，支援部分結算
- 首頁數字必須可信：範圍完整、標籤與內容一致
- 記帳輸入的操作步數不因模型變複雜而增加

**Non-Goals:**

- 不記錄個人開銷，因此本 app 內的共同卡累計金額**不等於**真實信用卡帳單總額
- 不做信用卡結帳日、帳單期別的建模
- 不做費用攤提（年繳保費不會被分攤到 12 個月）
- 不做應付帳款（帳單已到未付不會被認列）
- 不支援多幣別、不支援兩人以外的成員

## Decisions

### D1：付款方式取代 `paid_by` 三值契約

**選擇**：消費紀錄的付款方式為三選一 — 共同帳戶、共同卡、某人（Danny／PeiYu）。

| 付款方式 | 費用發生 | 共同帳戶現金流出 |
|---|---|---|
| 共同帳戶 | 消費日 | 同一天 |
| 共同卡 | 消費日 | 帳單扣款日 |
| Danny／PeiYu | 消費日 | 結算日 |

**理由**：三種方式的差別**只在現金何時流出**，這正是使用者要的「應計 vs 現金」區分。把它做成付款方式的固有屬性，使用者選完就自動成立，不需要額外欄位或理解。

個人帳戶與個人信用卡不區分，因為在「只記共同開銷」的前提下兩者結果相同：都是某人先出錢、共同帳戶欠他。差別只在那個人自己何時真的少錢，而那不在本 app 的記帳範圍內。

### D2：現金移動取代 `is_reimbursed`

**選擇**：新增現金移動紀錄，欄位為金額、日期、種類（入帳／共同卡帳單扣款／結算給某人）。移除 `is_reimbursed` 與 `reimbursed_at`。

**理由**：

- 結算實務上是「這個月一次結清」，逐筆勾選與真實行為不符
- boolean 無法表達部分結算（欠 20,000 只還 15,000）
- 現金移動有自己的日期，這是現金基礎唯一正確的時間來源；`reimbursed_at` 曾經存了這個資訊卻從未被使用

「待還墊付」因此變成推導值：某人的消費總額減去已結算給他的總額，不需要逐筆狀態。

### D3：首頁餘額拆成四行

**選擇**：

```
共同帳戶餘額        50,000     帳上真的有這麼多（現金）
  共同卡未出帳     −12,000     已刷、帳單未到（應計）
  待還墊付         −20,000     已花、未結算（應計）
  ─────────────
  可動用            18,000
```

**理由**：這是整個設計裡使用者唯一需要看懂的東西，而它不含任何會計詞彙。現行首頁只顯示第一行，且該行同時漏掉舊帳與待還墊付，會給出錯誤的安全感。

### D4：不建立信用卡結帳日與帳單期別模型

**選擇**：共同卡未出帳 = 累計共同卡消費 − 累計帳單扣款。帳單扣款由使用者輸入實際金額。

**理由**：3/20 刷的卡可能落在 4 月或 5 月帳單，取決於結帳日。建模需要結帳日、帳單週期、跨期歸屬三組規則，複雜度不符兩人專案的收益。以實際帳單金額扣款，差額自然留在未出帳，長期收斂。

**代價**：帳單日前後數天的「未出帳」數字會偏離真實卡片餘額。

### D5：只記共同開銷（範圍決定）

**選擇**：個人開銷不進本 app。

**理由**：使用者明確選擇。好處是每筆紀錄都是共同的，不需要額外的「共同／個人」欄位，也避免兩人看見彼此的私人消費。

**代價**：本 app 的共同卡累計金額不等於真實帳單，**帳單對帳功能不成立**——除非那張共同卡確實只用於共同開銷，此時金額才應該相符，對不上即代表有漏記。這是本設計唯一的自動偵錯機制，其可靠性取決於使用習慣。

### D6：報表以比較取代佔比

**選擇**：月報表主體從分類圓餅圖改為與前期平均的差異。

```
餐飲    12,400   比前三月平均多 3,200  ↑
交通     2,100   持平
娛樂     8,900   比前三月平均多 5,400  ↑↑
```

**理由**：「本月餐飲佔 30%」看完不會產生任何行動；「比平均多 3,200」會。使用者也表明圖表非必要，純文字即可滿足，同時可移除 Recharts 這個 client bundle 的大件。

### D7：結算入口放在首頁數字上，導覽縮為 3 格

**選擇**：首頁四行中的兩行負數本身即入口——點「共同卡未出帳」記帳單扣款，點「待還墊付」記結算。底部導覽從 `首頁／報表／FAB／分類／定期` 縮為 `首頁／報表／FAB`，分類與定期移入設定。

**理由**：結算是每月 1–3 次的低頻動作，不值得佔用主導覽，但它與「看到那個數字」同時發生，放在數字上是最短路徑。分類與定期都是設好就不動的維護動作，卻各佔一個主導覽位置，而九成的開啟目的是記一筆。

### D8：付款方式按鈕維持三個

**選擇**：表單顯示「共同帳戶／共同卡／我墊的」三個按鈕；「PeiYu 墊的」只在編輯他人紀錄時出現。

**理由**：通常誰付誰記，由 Danny 記錄 PeiYu 墊付的機率極低。選項數量與現行相同，資訊量卻增加一倍，不增加輸入摩擦。

## Risks / Trade-offs

### R1：共同卡帳單扣款忘記輸入（最高風險）

共同卡引入一個必須人工維護的狀態。若連續數月忘記輸入帳單扣款，「未出帳」會持續累積，「可動用」嚴重低估。低估比現行的高估更糟：高估至少讓人願意打開來看，低估會讓人不再信任這個數字而放棄使用。

**緩解**：帳單日推播提醒。但這正是 PWA 在 iOS 上最弱的環節（需加入主畫面、可靠性不佳）。**這是目前唯一一個可能需要原生 app 的理由**，且它是由共同卡這個決定引出的，不在原始需求清單內。

### R2：輸入摩擦

模型正確性提升的代價是每次記帳多一個判斷。若記帳中斷，帳不準的損失遠大於模型不精確。緩解方式為「上次使用的付款方式」預設與分類記憶，但實際效果需使用後驗證。

### R3：「共同卡只用於共同開銷」的假設

D5 的對帳機制依賴這個習慣。若共同卡偶爾用於個人消費，對帳會產生假警報，反而製造雜訊。

### R4：需求演進而非設計失誤

`'credit_card'` 三值設計在其提出時（2026-05-14）未必是錯的——若當時確實只有一張共同卡、也沒有個人卡墊付的情境，那是合理選擇。本次改動應理解為需求演進，而非前次流程失效。

## Migration Plan

既有 `transactions` 資料的轉換規則：

| 現有資料 | 轉換後 |
|---|---|
| `paid_by = 'shared'` | 付款方式 = 共同帳戶 |
| `paid_by = 'credit_card'` | 付款方式 = 共同卡 |
| `paid_by = <user uuid>` | 付款方式 = 該使用者 |
| `type = 'topup'` | 現金移動，種類 = 入帳 |
| `is_reimbursed = true` 的代墊 | 需產生對應的結算現金移動 |

`is_reimbursed = true` 的既有交易缺少可靠的結算日期（`reimbursed_at` 有值但從未被驗證過），轉換時以 `reimbursed_at` 為準；為 null 者以該筆交易的 `date` 代替，並在 migration 註記這批資料的日期為推估值。

歷史資料的正確性不影響未來使用，但會影響「過去某月實際現金流出」的回溯查詢，此限制需在 CONTEXT.md 標注。
